# Микросервис 1: Request Processor

## Назначение
Принимает запросы на отправку уведомлений, подготавливает сообщения и гарантированно доставляет их в соответствующие Kafka-топики через паттерн Transactional Outbox.

---

## Структура БД

Таблица: `notification_outbox` — хранилище сообщений для отправки в Kafka.

| Поле        | Тип        | Ограничения        | Значение по умолчанию | Описание                                           |
|-------------|------------|--------------------|------------------------|----------------------------------------------------|
| id          | UUID       | PK, NOT NULL       |                        | Идентификатор записи                               |
| created_at  | TIMESTAMP  | NOT NULL           | now()                  | Дата и время создания записи                       |
| topic       | VARCHAR    | NOT NULL           |                        | Название Kafka-топика (куда отправлять сообщение)  |
| key         | VARCHAR    | NOT NULL           |                        | Ключ сообщения (UUID в строковом виде)             |
| value       | TEXT       | NOT NULL           |                        | Тело сообщения (JSON)                              |
| sent        | BOOLEAN    | NOT NULL           | false                  | Флаг отправки                                      |
| attempt     | INTEGER    | NOT NULL           | 1                      | Количество попыток отправки                        |

---

## API

- Метод: POST
- Путь: `/api/v1/notifications`
- Тело запроса (JSON):
```json
{
  "type": "SMS|EMAIL|PUSH|TG_MESSAGE",
  "message": "string"
}
```

Коды ответов:
- 202 Accepted — запрос принят на обработку (сообщение помещено в outbox)
- 400 Bad Request — невалидный тип/сообщение
- 500 Internal Server Error — внутренняя ошибка обработки

---

## Логика обработки

Используется паттерн «Стратегия» для выбора обработчика по типу уведомления (`type`). Каждый обработчик:

1. Генерирует уникальный ключ сообщения: UUID (строка).
2. Формирует JSON-пayload.
3. Определяет целевой Kafka-топик:
    - SMS → `sms-events`
    - EMAIL → `email-events`
    - PUSH → `push-events`
    - TG_MESSAGE → `telegram-events`
4. Сохраняет запись в таблицу `notification_outbox` в рамках транзакции (Transactional Outbox).
5. Логирует:
    - `Подготовлено сообщение для отправки. Key: <key>, Payload: <body>, topic: <topic>`

Примечание: контроллер возвращает 202 сразу после успешной записи в outbox (фактическая отправка выполняется шедулером).

---

## Шедулер отправки сообщений

Периодически выбирает неотправленные записи из `notification_outbox` и публикует их в Kafka.

Параметры конфигурации (`application.yml`):
```yaml
outbox:
  batch-size: 50
  delay-ms: 1000
```

Логика работы:
1. С периодичностью `delay-ms` выбирает до `batch-size` записей, где `sent = false`, упорядоченных по `created_at` по возрастанию.
2. Пытается отправить каждую запись в Kafka (используя `topic` и `key`, `value` как payload).
3. При успешной отправке — обновляет запись: `sent = true`.
4. При ошибке — увеличивает `attempt` на 1 и оставляет запись «неотправленной» для повторной попытки в следующем цикле. Ошибку логирует с контекстом (key, topic, attempt, причина).

Рекомендации по надежности:
- Обеспечить идемпотентность продьюсера (например, ключ=UUID и корректная семантика в консюмерах).
- Ограничить максимальное число попыток (конфиг) и ввести DLQ/алертинг при превышении.
- Использовать транзакции БД при записи в outbox, а также гарантировать «одиночную» обработку в шедулере (locking/скан с mark-for-send).

## Минимальные требования к окружению

- PostgreSQL (или совместимая реляционная БД)
- Kafka-брокер
- Конфигурация приложения должна задавать bootstrap-servers Kafka и параметры outbox:
```yaml
spring:
  kafka:
    bootstrap-servers: localhost:9092

outbox:
  batch-size: 50
  delay-ms: 1000
```

## Диагностика и логирование

- Успех подготовки: `INFO Prepared message. Key=<key> Topic=<topic>`
- Успех отправки: `INFO Sent to Kafka. Key=<key> Topic=<topic>`
- Ошибка отправки: `WARN Send failed. Key=<key> Topic=<topic> Attempt=<attempt> Reason=<exception>`
- Повторные попытки происходят автоматически по расписанию шедулера.
